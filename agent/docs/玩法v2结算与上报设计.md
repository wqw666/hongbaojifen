## 背景与目标

v1 玩法只「自动回复 @」，不产生积分。v2 让玩法文件返回**每条消息的积分变动**，agent 在本地把游戏群内所有消息积成「局」，操作员在 GUI 一键**结算上报** → 总后台校验并逐事件实时入账（无人工审核环节，后端自动校验）。同时支持**多个游戏群**并行（每群独立成局），并处理执行器封禁/操作员停用时的停摆与恢复。

## 决策记录

| 决策点 | 结论 |
|---|---|
| 计分来源 | 玩法 .py 返回值扩展 v2：`{"reply", "delta"}` 或 `(reply, delta)`；v1 写法兼容（delta=0）。引擎把变动放 `engine.last_delta` |
| 局(round)粒度 | **每群一局**（群内同时只开一局），不是「每次结算新建」也不是跨群合并；局号 `round_id = G{群尾6位}-{MMddHHmmss}-{hex4}`（≤96 字符） |
| 事件缓冲上限 | `FLUSH_LIMIT=1000` 达阈值自动结算（防长局丢事件/内存失控）；`HARD_LIMIT=2000` 硬截断，先结算再继续 |
| 结算时机 | 手动「结算并上报」/「停止玩法」前先结算 / 事件数≥1000 自动结算 / GUI 重启 `_auto_restore` 续传未结算局 |
| 幂等 | 后端以 `round_id` 幂等（UNIQUE）；整局重复上报返回 `duplicate:true` 原记录，不重复入账 → agent 崩溃/断网重试安全 |
| 积分变动 vs 流水 | delta=0 只记回放不建流水；非 0 逐事件建流水，内部 biz_no=`game:{round_id}:{qq}`（V1.0.4 加宽 biz_no 列到 96 字符容纳） |
| 异常玩家 | 未知会员 / 会员已停用 / 余额不足 → 该事件按 delta=0 记入回放并累计 `warning`（不整局拒绝、不重复扣成功事件）；结算响应返回 `warning_count/warning` |
| 数据保留 | 游戏记录（局+事件回放）默认保留 30 天；`RetentionCleanupService` 每 6h 清理，dicts 键 `game_record_retention_days` 可改 |
| 停摆与恢复 | 总后台封禁执行器（40310，可「封禁并重置token」）/ 停用或禁手动操作员（40311）→ agent 引擎停、插件转发关、同步停；**本地局与事件保留**，后台解封后重开 GUI 自动恢复续传（token 被重置则 GUI 重填） |
| 停玩法安全 | 「停止玩法」先结算所有待报对局，全部成功才停；失败中止停止并保留事件，提示先「重试未上报」 |
| 成员注册 | 「启用玩法」可选勾自动注册：游戏群成员未建档者注册为会员（幂等），注册人 = 执行器绑定的操作员 QQ |
| token 漂移 | 每次结算线程先按 GUI 当前配置重造 client（吸收后端 reset-token 后的新值） |

## 对接契约（agent ↔ 总后台，v2 相关增量）

- `POST /api/open/games/report` `{executor_token, round_id, play_id?, play_name?, group_id?, events:[{qq, nickname?, msg?, reply?, delta}]}`（events ≤2000）
  → `{round_id, duplicate, member_count, total_delta, event_count, warning_count, warning}`；member_count = 结算时仍正常可入账的会员数
- 管理端：`GET /api/admin/game-records?group_id=&play_name=&page=&size=` 列表（record 含 round_id/executor_name/operator_qq/净积分/警告数…）+ `GET /api/admin/game-records/{id}` 完整回放 events
- 前置语义（本迭代一起收敛）：heartbeat 带 `admin_qq` 自动登记/续活**操作员**；群上报必带 `create_time` 并绑定执行器；`members/batch` 注册人 = 操作员 QQ；执行器封禁 `40310` / 操作员 40311 全链路生效
