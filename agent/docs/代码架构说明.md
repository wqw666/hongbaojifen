## 1. 总览

agent 是一个部署在 QQ 群侧 Windows 电脑上的程序，干三件事：

1. **监控/自动领取 QQ 钱包红包**，把每个红包的领取明细（谁领了、领了多少、什么时候）落本地盘；
2. 提供 GUI 供操作员扫码登录、设置群、看实时明细、查历史、导出 CSV；
3. **作为「执行器」对接总后台（hongbaojifen）**：周期心跳上报在线（心跳带本机登录 QQ → 总后台自动登记/续活**操作员**并记最近登录时间/来源 IP）、轮询远程命令并回报结果、把 QQ 群/群成员（自动注册为会员）同步进总后台；
4. **游戏玩法计分 + 结算上报**：从总后台拉玩法文件，在游戏群按规则自动回复并 @ 发言者；玩法返回积分变动，事件入局缓冲，GUI 结算后一次性上报总后台实时入账（见 §8）。

代码由 **三个互不耦合的部分** 组成：

| 部分 | 语言/框架 | 位置 | 作用 |
|---|---|---|---|
| GUI 桌面端 | Python 3.10+ / CustomTkinter | `agent/gui/` | 界面、线程调度、调插件 HTTP API |
| NapCat 插件 | TypeScript → Vite 打包成单个 `index.mjs` | `agent/plugin/` | 跑在 QQ 框架里，真正的抓包/抢包/查详情 |
| 对接包 | Python 纯 requests + 标准库 | `agent/integration/` | 与总后台通信（v1.1 新增，**独立于前两者**） |

三者关系：

```
┌─────────────── Windows ───────────────┐
│                                       │
│  GUI (gui/)          HTTP 127.0.0.1:6099        NapCat 插件 (plugin/)
│  CustomTkinter  ────────────────────►  ─────────────────────────┐
│  MainWindow · 8 tabs                 /plugin/napcat-           │ 挂内核监听，真正
│  BackendTab   ◄──── after(0) ────────  plugin-cleaner/api/**    │ 抓红包/抢红包/查详情
│                                       │  ▲                      │
│  integration/ (总后台对接包)           │  │ 读 redpackets.json   │  QQ 群消息/事件
│  HbjfClient/SyncWorker                │  └──────────┐           │
└───────┬───────────────────────────────┘             │           ▼
        │ HTTP :8892 (X-Api-Key)        ┌─────────────┴───┐   QQ 服务器
        ▼                               │ redpackets.json │
  总后台 hongbaojifen                    └─────────────────┘
  (Spring Boot，本仓库上级目录，不属 agent)
```

> 术语：「总后台」= hongbaojifen 仓库（Spring Boot 后端 + React 管理前端），agent 通过 `/api/open/**` 开放接口 + `X-Api-Key` 请求头对接，详见 [与总后台对接](#7-与总后台hongbaojifen对接integration)。

## 3. 启动链

### 3.1 打包后（交付机器）

```
双击「一键启动.bat」（agent\）
  │  ① 若同目录存在 agent.exe → start "" agent.exe 直接开 GUI（release 布局）
  │  ② 否则（源码布局）→ call start_silent.bat
  ▼
start_silent.bat（全程无回显）
  ① 同步插件：plugin\dist\index.mjs  → copy → tools\NapCat\plugins\napcat-plugin-cleaner\index.mjs
  ② 杀旧引导进程：taskkill /F /IM NapCatWinBootMain.exe /T，timeout 3 秒
  ③ wscript //nologo restart_napcat_hidden.vbs
       └─ vbs 内部：再 taskkill NapCatWinBootMain → 等 2s
          → call launcher-win10-user.bat（NapCat 扫码登录模式，窗口隐藏）
  ④ 轮询等待插件就绪：每 3s GET http://127.0.0.1:6099/plugin/napcat-plugin-cleaner/api/status
     直到 HTTP 200（上限 30 次 ≈ 90 秒）
  ⑤ start "" agent.exe   ← GUI 主程序
```

- 「启动.vbs」= 无黑窗版：隐藏窗口执行 `start_silent.bat`（日常推荐双击它）。
- NapCat 每次都是**扫码登录模式**启动（vbs 不传 QQ 号），登录态不落包；「每台机器独立扫码登录」是设计约束（`scripts/assemble_release.py` 打包时专门 strip 登录态，见 §9）。
- GUI 内部「启动 NapCat」按钮走同一条 vbs（`main_window.py:227 launch_napcat`，先停监控轮询 → `subprocess.Popen(["wscript","//nologo",vbs])` → 切扫码页开始轮二维码），即 GUI 能自愈拉起被关掉的 NapCat。

### 3.2 开发模式

```
run_dev.bat：找 Python → pip install -r requirements.txt → cd gui && python main.py
```

`gui/main.py` 开头的 `_bootstrap_paths()`（9-16 行）会把仓库根目录塞进 `sys.path` —— 因为对接包 `integration/` 在 `gui/` 上一级，PyInstaller 打包时则靠 spec 的 `pathex`（见 §9），两种运行方式下 import 都不缺。

### 3.3 一次性安装（每台机器）

`tools\setup_napcat.bat "NapCat解压目录"`：把官方 NapCat 完整包 `robocopy /E` 进 `tools\NapCat\`。因为 **NapCat 含登录态与密钥，不入 git**，仓库里只有安装脚本。

### 4.3 线程模型（全文纪律一致，务必遵守）

**纪律**（写在 `backend_tab.py:10-11`、`sync_worker.py:13-16`）：

> 所有网络操作放临时 daemon 线程里跑；线程里**绝不碰控件**；结果一律 `self.after(0, 回调)` 扔回 UI 线程改界面。

理由：Tkinter 不是线程安全的，两个线程同时碰控件会随机崩。代价是每个按钮动作拆成「worker 线程 + after(0) 回填」两步，代码里出现频率极高。

`main_window.py` 所有建线程的点（全部 daemon=True，都是网络操作）：

| 行 | 方法 | 干什么 |
|---|---|---|
| 322 | `refresh_login_qrcode` | WebUI ping/登录态/二维码 |
| 364 | `_fill_quick_login_buttons` | 取快捷登录 QQ 列表 |
| 792 | `sync_settings` | 同步设置到插件 |
| 816 | `refresh_status` | `get_status` → 更新状态区 |
| 895 | `apply_multi_group_watch` | 应用多群抢包 |
| 943 | `refresh_monitor` | 刷新监控列表 |
| 969 | `clear_monitor_records` | 清空插件记录 |
| 1118 | `load_group_members` | 加载群成员 |
| 1219 | `refresh_selected_detail` | 补拉某红包详情 |
| 1269 | `run_query` | 历史查询 |

两条 **after() 自调度链**（GUI 的“心跳”）：

- **监控轮询**（1319-1328）：`_start_poll` 置开关 → `_schedule_poll` 每轮先 `refresh_monitor()` 再 `after(间隔秒×1000)` 排下一轮。默认 2 秒一次，`poll_interval_sec` 配置可调；开关一关链就断。监控页「轮询时间」label 实时显示它。
- **登录轮询**（268-275）：每 2500ms 静默刷二维码，直到登录成功。

关窗清理清单 `_on_close`：断监控轮询 → `after_cancel` 两个轮询句柄 → `backend_tab.shutdown()`（停总后台线程，见 §7.4）→ `play_tab.shutdown()`（停玩法回调服务 + worker，见 §8.3）→ destroy。**新增 tab 若建了线程，必须在 _on_close 里加清理，否则残留 daemon 线程刷事件。**

### 4.4 关键流程串讲

- **登录**：`refresh_login_qrcode`(277) worker 线程拿二维码 → 用户扫码 → `_apply_login_ui`(324) 发现已登录 → 取消登录轮询 → `refresh_status`(340) → 点「部署插件并进入监控」→ `_after_login_setup`(382)：`deploy_plugin` → `sync_settings` → 切监控 tab → `refresh_status + refresh_monitor`。
- **状态自愈**：`refresh_status`(809) 失败（NapCat 没起/插件没就绪）→ 自动转扫码登录页 + 重开登录轮询 + 静默刷二维码。启动期 NapCat 的 503/404 噪音经 `_is_startup_noise`(27-41) 转成友好文案而非刷屏报错。
- **一键清空**：`clear_monitor_records`(945) 先断轮询（防清的过程中又写入）→ worker 清插件 → 清两棵树 → finally 恢复轮询。插件端清空失败时 GUI 走 fallback：重新部署插件 + 直接写空 `redpackets.json` + WebUI `reload_plugin`（api_client 231）。

### 5.2 生命周期（index.ts）

### 5.3 红包是怎么被抓到并抢掉的（核心链路）

```
QQ 群来红包消息
  │ attachKernelMsgListener (redpacket.ts:390) 经 NapCat eventWrapper 挂内核 3 个回调：
  │   onRecvMsg(432) / onAddSendMsg(437) / onMsgInfoListUpdate(442，只处理含红包的消息)
  ▼
onRawRedPacketMessage (api.ts:1683)
  ▼ extractWalletFromRaw (redpacket.ts:80) —— 红包判定字段：
  │   · 消息元素 elementType === 9（wallet 元素）：w.redBag?.billNo / redChannel / authKey /
  │     receiver?.title（祝福语 wishing）
  │   · 领取灰条 grayTipElement.jsonGrayTipElement.busiId === '19357'（别人领了）
  ▼
handleWallet (api.ts:1698)
  ├─ 非群聊且非灰条 → 丢弃；watchGroups 白名单不过 → 丢弃
  ├─【灰条分支】extractGrayTipClaim 追加领取人 → upsertRecord；
```

## 7. 与总后台（hongbaojifen）对接（integration/）

### 7.1 为什么独立成包

总后台架构约定（本迭代约束）：**总后台架构和代码不动**，agent 侧对接代码**单独写、尽量不影响老 GUI**。所以：

- `integration/` 是纯 Python 包：**只依赖 requests + 标准库**，import 它不会触发 GUI/插件模块；
- GUI 依赖方向是单向的：`BackendTab` 构造时把 GUI 的数据源以 **duck-typed provider（函数/回调）注入**，integration 不知道 GUI 的存在 → 可脱离 GUI 单独测试（smoke.py 就是这么跑的）；
- 所有总后台错误统一抛 `BackendError`（backend_client.py），GUI 层只管翻译成中文提示。

### 7.2 模块

| 模块 | 职责 |
|---|---|
| `backend_client.py` | `HbjfClient(base_url, api_key, token)`：带 `X-Api-Key` 头的 Session；方法 = 总后台 open 接口逐条映射：`heartbeat`/`upsert_group`/`list_groups`/`upsert_qq_account`/`list_qq_accounts`/`delete_qq_account`/`register_members_batch`/`query_points_batch`/`poll_commands`/`report_command_result`/`list_rules`/`download_rule`/`report_game_round`（对局结算上报）等；`ExecutorBanned`/`OperatorDisabled` 子类区分 40310/40311。code≠0 / HTTP≥400 / 连不上 → `BackendError` |
| `sync_worker.py` | `SyncWorker`（daemon 线程）：周期 tick = 心跳 → 拉远程命令 → 逐条执行并回报 → 若开了自动同步且距上次 ≥300s → 跑会员同步。心跳经 `admin_qq_provider` 携带本机登录 QQ（操作员自动登记/续活）；命中 40310/40311 → 停止循环并 emit `("banned", 原因)`（GUI 转红字停摆）。v1 命令执行器 `_execute`：`get_status` / `set_config`（白名单键：`heartbeat_interval_sec`/`member_group_id`/`auto_sync_members`，改完 save_config + 同步插件配置）/ `sync_members` |

### 7.3 会员同步算法（member_sync.py）

「选一个群作会员群 → agent 把群成员同步成总后台会员」的核心：

```
run_member_sync(client, group_id, members_provider, on_progress)
  ① 拉群成员 [{qq/nickname/card/role…}]（GUI 从插件 /members 取；_member_qq 兼容
     qq|user_id|uin，_member_nick 兼容 nickname|card）
  ② 去重合法 QQ；按 role 推导群主 owner + 管理员 admin_qqs
  ③ client.upsert_group(..., create_time=群创建时间)  ← 群信息+创建时间也上报（绑定执行器）
  ④ 每 500 个一批 client.query_points_batch(qqs)
       → exists=true 的算「已建档」；exists=false 的是「未注册」
  ⑤ 未注册者每 500 个一批 client.register_members_batch(...) 注册为会员（后端记注册人=操作员QQ）
  ⑥ 返回 {total, added, existed, skipped, warning}
```

**幂等**：整个流程天然幂等（重复跑：查询全部 exists → 不重复注册），符合命令通道「5 分钟重投必须幂等」的契约。

### 7.4 GUI「总后台对接」tab（backend_tab.py）

## 8. 游戏玩法计分 + 结算上报（玩法引擎 v2，GUI「游戏玩法」Tab）

> 完整设计：[玩法v2结算与上报设计.md](玩法v2结算与上报设计.md)；总后台入账/回放契约见仓库根 README「游戏对局结算」。「游戏玩法」是「总后台对接」右侧的独立 tab。

在总后台「会员玩法管理」上传玩法 `.py` 文件 → 本 agent 拉取后在**游戏群**（可多个）自动回复并计分：群成员发言 → 机器人按玩法算回复并 @ 发言者；玩法返回的积分变动先记入本地**当前局**，GUI 结算时一次性上报总后台入账。**群主/管理员（NapCat 登录 QQ）也是玩家**（只有机器人自己的发言不触发，防回环）。回复架构 = agent Python 玩法引擎（玩法文件即 Python 源码，最灵活）。

### 8.1 消息流（三段 + 局缓冲）

```
QQ 群消息 → NapCat 插件 play.ts  handlePlayMessage(play.ts)
  过滤：post_type=message（自己发的 message_sent 一律不转发，防 n+1 回环）、
       message_type=group、config.playEnabled、群在白名单 playGroups、
       纯文本非空、qq ≠ self_id
  → POST 本地回调（默认 http://127.0.0.1:6101/play/msg，2s 超时，失败静默丢弃）
      ↓
GUI play_tab 本地 ThreadingHTTPServer（127.0.0.1:play_callback_port）
  → 入队 _msg_queue → daemon worker 线程（_worker_loop）
  → RuleEngine.handle_message（play_engine.py）：同 qq 1s 去重 → 热重载检查
    → 锁外执行玩法 handle_message()（防玩家代码持锁卡死）→ (reply | None, engine.last_delta)
      ↓（有回复）
  POST 插件 /play/reply {group_id, at_qq, text}
      ↓
play.ts /play/reply 校验 playEnabled+群白名单 → actions.call send_group_msg，
  message = [at qq] + [text] → 群成员看到机器人回复
      ↓（本条若有回复或 delta≠0，且玩法在启用中）
RoundSession.add_event(qq, nickname, msg, reply, delta) → 该群「当前局」缓冲
      ↓（结算时机：手动「结算并上报」/ 停止玩法 / 事件数≥1000 自动）
settle → POST /api/open/games/report {round_id, play_id, play_name, group_id, events}
  → 总后台逐事件入账（round_id 幂等：重传返回 duplicate 不重复入账）
```

### 8.2 玩法文件协议 v2 与引擎（integration/play_engine.py）

```python
def handle_message(group_id: int, qq: int, nickname: str, text: str):
    """返回：
    None                        = 不回复
    "回复文本"                    = v1 写法兼容（积分变动 0）
    {"reply": "文本", "delta": n} 或 ("文本", n)  = v2：delta>0 加分 / <0 扣分 / 0 只记过程
    """
```

- `RuleEngine` 单例（play_tab 持有）。`activate(rule_id, rule_name, file_path)` 试加载，失败返回错误文本且不激活；`deactivate`；每次 `handle_message` 后的积分变动落在 `self.last_delta`（v1 玩法恒 0，单 worker 串行线程安全）
- **热重载**：每次 stat 文件 mtime，变了就重 import（模块名 `_play_rule_{id}_{stem}`，先 `sys.modules.pop` 丢旧模块）；总后台重传 → agent 重新下载覆盖 → 下次发言即新逻辑；加载失败沿用旧版并记 `last_error`
- **去重**：同 qq 1 秒内重复发言直接忽略（`DEDUP_WINDOW_SEC=1.0`）；玩法代码抛异常只记 `last_error` 并放弃本条，不崩引擎
- GUI 玩法页存 `%APPDATA%\QQHongbaoMonitor\plays\rule_{id}.py`；样本玩法在 `play_rules/`（rule_add1 数字+1 / rule_add2 数字+2，v1 无积分版）
- **自测**：`python -m integration.play_engine`（激活/加减/非数字/v1&v2 返回值/delta 落位/去重/热重载/坏文件/缺入口/RoundSession 多局结算/deactivate，优先读仓库真实样本）

### 8.3 GUI「游戏玩法」tab 与 RoundSession（gui/app/play_tab.py）

`PlayTab(ctk.CTkScrollableFrame)`，构造时即拉起本地回调服务 + worker（daemon）；`shutdown()` 在 `_on_close` 调用。布局：玩法选择（刷新列表→OptionMenu，数据源 `HbjfClient.list_rules`）、游戏群号（**逗号分隔多群**）+ 自动注册会员勾选、按钮「启用玩法 / 停止玩法（先结算）/ 结算并上报 / 重试未上报」、每群状态行、日志框。

- **每群独立成局**：`RoundSession` 维护每群的当前局，`round_id = G{群尾6位}-{MMddHHmmss}-{hex4}`，事件逐个落进局缓冲（`add_event`），`settle(group_id)` 把整局上传 → 成功才开新局
- 缓冲阈值：`FLUSH_LIMIT=1000`（软，事件数达阈值自动结算）/ `HARD_LIMIT=2000`（硬，超过拒绝新事件，提示先结算）
- `_settle_groups`（后台线程）：结算前先用最新配置重造 `HbjfClient`（吸收总后台重置过的 token）→ 逐群 settle；任一失败**保留本地 events** 供「重试未上报」，不被静默丢弃
- 幂等兜底：即使本地以为失败但后端已入账（网络断在半路），重试上报 round_id 相同 → 后端 `duplicate:true` 不重复入账
- 「启用玩法」：下载玩法文件（覆盖=总后台最新版）→ POST 插件 `/play/config {enabled:true, groups:[...], callback}`（失败即中止）→ engine.activate → 可选跑会员同步 → cfg 落盘（含 `play_auto_register_members`）
- 「停止玩法」：先结算全部待报对局，**全部成功才停**（deactivate + 插件 config enabled:false + cfg 清 play_enabled，保留 rule/group 供恢复）；有失败则中止停止并提示先重试
- **封禁/停用停摆**：总后台封禁执行器（40310）/停用或禁手动操作员（40311）→ `_mark_banned`：引擎停、插件转发关、cfg.play_enabled=false（局与事件保留）；GUI 红字提示 + 日志引导去总后台处理；解封后重启 GUI（或重新启用）自动恢复：重拉最新玩法文件 + 续传未结算局（`_auto_restore`）
- 重启 GUI 自动恢复（`_auto_restore`）：cfg.play_enabled 时重下载 + 插件转发 + 激活 + 自动同步成员 + 续传局

### 8.4 触发范围决策

全体成员触发（含群主/管理员/机器人使用者），**唯独机器人自己（post_type=message_sent 或 qq==self_id）不触发** —— 双保险写在 play.ts:46-54。玩法文件可自行用 qq/nickname 判断要不要理某人（协议参数都传了）；要扣/加积分的玩法按 v2 返回 delta，玩法自己负责算分逻辑。

## 9. 打包系统

两个入口，都在 `agent\` 目录双击：

| | `打包exe.bat` | `build.bat` |
|---|---|---|
| 用途 | **快速出 exe 测试** | 完整交付包 |
| 步骤 | 定位 Python → 备 plugin_bundle（有 plugin\dist 就同步，没有就复用旧的）→ pip install → PyInstaller spec | `[1/5]` 插件 npm 构建（dist 已存在则跳过，无需 Node）→ `[2/5]` 备 plugin_bundle → `[3/5]` pip → `[4/5]` PyInstaller → `[5/5]` assemble_release.py 组装 |
| 产物 | `dist\agent.exe`（几十秒） | `release\`（解压即用）+ 根目录 `agent_交付包.zip`（几分钟） |
| 迭代建议 | 改 Python 代码后反复跑它 | 涉及插件/交付再跑 |

**PyInstaller spec 关键点（QQHongbaoMonitor.spec）**：

- `Analysis([gui/main.py], pathex=[GUI, ROOT], ...)` —— **仓库根必须进 pathex**，否则顶层 `integration/` 包进不了 exe（最易踩的坑）；
- datas：customtkinter 主题资源 + `(plugin_bundle, "plugin_bundle")` —— 插件 index.mjs 内嵌进 exe，部署插件时解出来（`sys._MEIPASS/plugin_bundle`）；
- excludes：numpy/cryptography/psutil 等重型无用依赖（缩体积）；
- `EXE(... console=False)`：onefile 无控制台。

**assemble_release.py（build.bat 第 5 步）**：清空重建 `release/` → `dist/*.exe` 拷成 `release/agent.exe` → 拷启动脚本 → `copytree tools/NapCat` 并 **strip 登录态**（删 cache/qrcode.png、guild1.db*、napcat_*.json、onebot11_*.json、passkey.json、logs —— 每台部署机独立扫码登录的设计就靠它）→ 预置插件 → 拷全部源码镜像进 `release/agent/`（gui/plugin/src/integration/client/scripts/plugin_bundle + 构建脚本 + README）→ 生成 `使用说明.txt`（utf-8-sig，Windows 记事本友好）→ 打 `agent_交付包.zip`（UTF-8 文件名）。

`write_release_doc.ps1`：独立生成使用说明的 PowerShell（文案更详），可单独跑刷新 release 里的文档。
