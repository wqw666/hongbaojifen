## 1. 总览

agent 是一个部署在 QQ 群侧 Windows 电脑上的程序，干三件事：

1. **监控/自动领取 QQ 钱包红包**，把每个红包的领取明细（谁领了、领了多少、什么时候）落本地盘；
2. 提供 GUI 供操作员扫码登录、设置群、看实时明细、查历史、导出 CSV；
3. **作为「执行器」对接总后台（hongbaojifen）**：周期心跳上报在线（心跳带本机登录 QQ → 总后台自动登记/续活**操作员**并记最近登录时间/来源 IP）、轮询远程命令并回报结果、把 QQ 群/群成员（自动注册为会员）同步进总后台；
4. **游戏玩法计分 + 结算上报**：自动拉取总后台唯一「复合玩法」（rule_fuhe.py），玩法面板手动驱动每局（开始本局/停止下注封盘/红包开奖/结算上报）；群内下注与撑庄文字即时 @ 回复，积分只经红包领取后的结算一次性上报总后台入账（见 §8）。

代码由 **三个互不耦合的部分** 组成：

| 部分 | 语言/框架 | 位置 | 作用 |
|---|---|---|---|
| GUI 桌面端 | Python 3.10+ / CustomTkinter | `agent/gui/` | 界面、线程调度、调插件 HTTP API |
| NapCat 插件 | TypeScript → Vite 打包成单个 `index.mjs` | `agent/plugin/` | 跑在 QQ 框架里，真正的抓包/抢包/查详情 |
| 对接包 | Python 纯 requests + 标准库 | `agent/integration/` | 与总后台通信（v1.1 新增，**独立于前两者**） |

三者关系：

```
┌─────────────── Windows ───────────────┐
│                                       │
│  GUI (gui/)          HTTP 127.0.0.1:6099        NapCat 插件 (plugin/)
│  CustomTkinter  ────────────────────►  ─────────────────────────┐
│  MainWindow · 7 tabs                 /plugin/napcat-           │ 挂内核监听，真正
│  BackendTab   ◄──── after(0) ────────  plugin-cleaner/api/**    │ 抓红包/抢红包/查详情
│                                       │  ▲                      │
│  integration/ (总后台对接包)           │  │ 读 redpackets.json   │  QQ 群消息/事件
│  HbjfClient/SyncWorker                │  └──────────┐           │
└───────┬───────────────────────────────┘             │           ▼
        │ HTTP :8892 (X-Api-Key)        ┌─────────────┴───┐   QQ 服务器
        ▼                               │ redpackets.json │
  总后台 hongbaojifen                    └─────────────────┘

## 3. 启动链

### 3.1 打包后（交付机器）

```
双击「一键启动.bat」（agent\）
  │  ① 若同目录存在 agent.exe → start "" agent.exe 直接开 GUI（release 布局）
  │  ② 否则（源码布局）→ call start_silent.bat
  ▼
start_silent.bat（全程无回显）
  ① 同步插件：plugin\dist\index.mjs  → copy → tools\NapCat\plugins\napcat-plugin-cleaner\index.mjs
  ② 杀旧引导进程：taskkill /F /IM NapCatWinBootMain.exe /T，timeout 3 秒
  ③ wscript //nologo restart_napcat_hidden.vbs
       └─ vbs 内部：再 taskkill NapCatWinBootMain → 等 2s
          → call launcher-win10-user.bat（NapCat 扫码登录模式，窗口隐藏）
  ④ 轮询等待插件就绪：每 3s GET http://127.0.0.1:6099/plugin/napcat-plugin-cleaner/api/status
     直到 HTTP 200（上限 30 次 ≈ 90 秒）
  ⑤ start "" agent.exe   ← GUI 主程序
```

- 「启动.vbs」= 无黑窗版：隐藏窗口执行 `start_silent.bat`（日常推荐双击它）。
- NapCat 每次都是**扫码登录模式**启动（vbs 不传 QQ 号），登录态不落包；「每台机器独立扫码登录」是设计约束（`scripts/assemble_release.py` 打包时专门 strip 登录态，见 §9）。
- GUI 内部拉起 NapCat 走同一条 vbs（`main_window.py:410 launch_napcat`：登录页「启动 QQ 环境并扫码登录」按钮 / 初启自动拉起都进它——先停监控轮询 → `subprocess.Popen(["wscript","//nologo",vbs])` → 每 2.5s 轮二维码；vbs 每次先杀旧引导进程再拉新，可自愈）。**退出登录 = 杀 QQ 与 NapCat 后不自动重启**（`logout_qq`(348)），要重新使用由用户点「启动」按钮显式拉起。

### 3.2 开发模式

```
run_dev.bat：找 Python → pip install -r requirements.txt → cd gui && python main.py
```

`gui/main.py` 开头的 `_bootstrap_paths()`（9-16 行）会把仓库根目录塞进 `sys.path` —— 因为对接包 `integration/` 在 `gui/` 上一级，PyInstaller 打包时则靠 spec 的 `pathex`（见 §9），两种运行方式下 import 都不缺。

### 3.3 一次性安装（每台机器）

`tools\setup_napcat.bat "NapCat解压目录"`：把官方 NapCat 完整包 `robocopy /E` 进 `tools\NapCat\`。因为 **NapCat 含登录态与密钥，不入 git**，仓库里只有安装脚本。

### 4.3 线程模型（全文纪律一致，务必遵守）

**纪律**（写在 `backend_tab.py:10-11`、`sync_worker.py:13-16`）：

> 所有网络操作放临时 daemon 线程里跑；线程里**绝不碰控件**；结果一律 `self.after(0, 回调)` 扔回 UI 线程改界面。

理由：Tkinter 不是线程安全的，两个线程同时碰控件会随机崩。代价是每个按钮动作拆成「worker 线程 + after(0) 回填」两步，代码里出现频率极高。

`main_window.py` 所有建线程的点（全部 daemon=True，都是网络操作）：

| 行 | 方法 | 干什么 |
|---|---|---|
| 474 | `refresh_login_qrcode` | WebUI ping/登录态/二维码（`force_refresh`=按钮向 QQ 要新码；轮询自动刷过期码） |
| 353/407 | `logout_qq`/`_after_logout_done` | 杀 QQ+NapCat 不自动重启，登录页交还「启动」按钮 |
| 1618 | `sync_settings` | 同步设置到插件 |
| 1645 | `refresh_status` | `get_status` → 更新状态区 |
| 1705 | `apply_multi_group_watch` | 应用多群抢包 |
| 1743 | `refresh_monitor` | 刷新监控列表 |
| 1784 | `clear_monitor_records` | 清空插件记录 |
| 1928 | `load_group_members` | 加载群成员 |
| 2036 | `refresh_selected_detail` | 补拉某红包详情 |
| 2060 | `run_query` | 历史查询 |

两条 **after() 自调度链**（GUI 的“心跳”）：

- **监控轮询**（`_start_poll`(2150)/`_schedule_poll`(2154)）：`_start_poll` 置开关 → `_schedule_poll` 每轮先 `refresh_monitor()` 再 `after(间隔秒×1000)` 排下一轮。默认 2 秒一次，`poll_interval_sec` 配置可调；开关一关链就断。监控页「轮询时间」label 实时显示它。
- **登录轮询**（`_login_poll_tick`(470)）：每 2500ms 调一次 `refresh_login_qrcode(silent=True)`（登录态/二维码/过期自动刷新），直到登录成功或用户退出登录（logout 时两条链都断，重启环境由「启动」按钮重新拉起）。

关窗清理清单 `_on_close`：断监控轮询 → `after_cancel` 两个轮询句柄 → `backend_tab.shutdown()`（停总后台线程，见 §7.4）→ `play_tab.shutdown()`（停玩法回调服务 + worker，见 §8.3）→ destroy。**新增 tab 若建了线程，必须在 _on_close 里加清理，否则残留 daemon 线程刷事件。**

### 4.4 关键流程串讲

- **登录**：打开软件 `_auto_env_start`(307) 检测服务 → 未就绪自动经 `launch_napcat`(415) 拉起（登录页「启动 QQ 环境并扫码登录」按钮同步出现，退出登录后/自动拉起失败时放开供手动重试）→ `refresh_login_qrcode`(474) worker 线程每 2.5s 取状态：二维码按 URL 现渲染、`loginError` 带「过期」自动 `RefreshQRcode`（60s 节流）、按钮点「刷新二维码」= `force_refresh` 向 QQ 要新码 → 用户扫码 → `_apply_login_ui`(561) 发现已登录 → 取消登录轮询 → `_after_login_auto`(612)：`deploy_plugin` → 同步设置 → `_enter_main_after_login`(645) 切主界面。
- **退出登录 / 换 QQ**：主界面右上角「退出登录」→ `logout_qq`(353) 停两条轮询 → 线程杀 `NapCatWinBootMain.exe`/`QQ.exe` 整树并等 QQ 进程消失（最长 ~15s）→ `_after_logout_done`(407)：状态「已退出登录」+ 放开「启动」按钮，**不自动重启**（此前自动重启到扫码页曾因二维码图片停在 NapCat 过期缓存 png 上而无法扫码/刷新，已改为按 URL 渲染根治）。换号 = 点「启动」→ 出新码 → 扫码。
- **状态自愈**：`refresh_status`(1645) 失败（NapCat 没起/插件没就绪）→ 自动转扫码登录页 + 重开登录轮询 + 静默刷二维码。启动期 NapCat 的 503/404 噪音经 `_is_startup_noise` 转成友好文案而非刷屏报错。
- **一键清空**：`clear_monitor_records`(1784) 先断轮询（防清的过程中又写入）→ worker 清插件 → 清两棵树 → finally 恢复轮询。插件端清空失败时 GUI 走 fallback：重新部署插件 + 直接写空 `redpackets.json` + WebUI `reload_plugin`（api_client 231）。

## 7. 与总后台（hongbaojifen）对接（integration/）

### 7.1 为什么独立成包

总后台架构约定（本迭代约束）：**总后台架构和代码不动**，agent 侧对接代码**单独写、尽量不影响老 GUI**。所以：

- `integration/` 是纯 Python 包：**只依赖 requests + 标准库**，import 它不会触发 GUI/插件模块；
- GUI 依赖方向是单向的：`BackendTab` 构造时把 GUI 的数据源以 **duck-typed provider（函数/回调）注入**，integration 不知道 GUI 的存在 → 可脱离 GUI 单独测试（smoke.py 就是这么跑的）；
- 所有总后台错误统一抛 `BackendError`（backend_client.py），GUI 层只管翻译成中文提示。

### 7.2 模块

| 模块 | 职责 |
|---|---|
| `backend_client.py` | `HbjfClient(base_url, api_key, token)`：带 `X-Api-Key` 头的 Session；方法 = 总后台 open 接口逐条映射：`heartbeat`/`upsert_group`/`list_groups`/`upsert_qq_account`/`list_qq_accounts`/`delete_qq_account`/`register_members_batch`/`query_points_batch`/`poll_commands`/`report_command_result`/`list_rules`/`download_rule`/`report_game_round`（对局结算上报）等；`ExecutorBanned`/`OperatorDisabled` 子类区分 40310/40311。code≠0 / HTTP≥400 / 连不上 → `BackendError` |
| `sync_worker.py` | `SyncWorker`（daemon 线程）：周期 tick = 心跳 → 拉远程命令 → 逐条执行并回报 → 若开了自动同步且距上次 ≥300s → 跑会员同步。心跳经 `admin_qq_provider` 携带本机登录 QQ（操作员自动登记/续活）；命中 40310/40311 → 停止循环并 emit `("banned", 原因)`（GUI 转红字停摆）。v1 命令执行器 `_execute`：`get_status` / `set_config`（白名单键：`heartbeat_interval_sec`/`member_group_id`/`auto_sync_members`，改完 save_config + 同步插件配置）/ `sync_members` |
| `member_sync.py` | `run_member_sync(client, group_id, members_provider, on_progress, ...)` —— 算法见下，**纯函数式、可单测**；异常提升级为可停摆类型 |
| `auth.py` | `register_self_admin_qq(client, login_info_provider)`：读本机登录 QQ（NapCat get_login_info / 插件 get_status 的 `uin`，缓存 60s）→ 上报为操作员 QQ。「**通过 agent 登录并连接总后台的都是操作员**」这条业务规则落在这（心跳也会自动走同一条 upsert） |
| `smoke.py` | 全链路冒烟：心跳→群上报+列表→（可选）操作员QQ上报→（可选）假成员会员同步→命令 poll→（可选）对局上报+round_id 幂等。`python -m integration.smoke --base ... --key ... --token <执行器token> [--self-qq ... --member-count N --play-events N]` |
| `play_engine.py` | 玩法引擎：`RuleEngine`（v1 str 兼容 + v2 dict/tuple 返回积分变动 → `engine.last_delta`；`call_rule(fn_name, gid, *args)` 原样透传带返回值协议）+ `RoundSession`（v2 遗留多局缓冲类，v3 复合玩法不启用，见 §8.2） |

### 7.3 会员同步算法（member_sync.py）

「选一个群作会员群 → agent 把群成员同步成总后台会员」的核心：

```
run_member_sync(client, group_id, members_provider, on_progress)
  ① 拉群成员 [{qq/nickname/card/role…}]（GUI 从插件 /members 取；_member_qq 兼容
     qq|user_id|uin，_member_nick 兼容 nickname|card）
  ② 去重合法 QQ；按 role 推导群主 owner + 管理员 admin_qqs
  ③ client.upsert_group(..., create_time=群创建时间)  ← 群信息+创建时间也上报（绑定执行器）
  ④ 每 500 个一批 client.query_points_batch(qqs)
       → exists=true 的算「已建档」；exists=false 的是「未注册」
  ⑤ 未注册者每 500 个一批 client.register_members_batch(...) 注册为会员（后端记注册人=操作员QQ）
  ⑥ 返回 {total, added, existed, skipped, warning}
```

**幂等**：整个流程天然幂等（重复跑：查询全部 exists → 不重复注册），符合命令通道「5 分钟重投必须幂等」的契约。

| 运行日志 | 500 行截断日志框 |

去重后本页不再提供「会员群 / 操作员QQ / 群列表」卡片（2026-09-07 删除，v-02）：

- **会员群同步**：入口统一在「群管理/会员」页（main_window 内建 `run_member_sync`/`upsert_group` 路径，群号在群管理页单点维护）；本页只保留 `_fetch_payload/_members_provider/_group_provider` 数据提供者（60s payload 缓存），供 `SyncWorker` 心跳期间执行总后台远程「同步会员」命令与自动会员同步使用。
- **操作员QQ**：= 本机登录并连总后台的 QQ，对接启动后自动随心跳登记/续活（`admin_qq_provider` → `_login_info`，NapCat WebUI `get_login_info` 60s 缓存），不再需要本页手管/手动上报（原 `_refresh_qqs/_add_qq/_del_qq/_upload_self_qq` 及 UI 一并删除）。

`_fetch_payload` 把插件 `/status` + `/members` 结果（含群创建时间 `group_create_time_str`）缓存 60s，供成员列表/群上报/玩法页共用。

`_mark_banned(reason)`（`kind == "banned"` 时在任何线程触发）：UI 线程置红字停摆态 + 日志引导；封禁/停用期间不再心跳/同步，避免刷 403x；后台解封后重新「启动对接」即恢复。

关闭钩子 `shutdown()`：`worker.stop_worker()`（Event 置位 + join ≤2s）+ 玩法页 shutdown，在 `_on_close` 里调用，**不调用会残留 daemon 线程继续刷日志**。

```

```

## 8. 游戏玩法计分 + 结算上报（玩法 v3：复合玩法唯一化，GUI「游戏玩法」手动操作台）

> **2026-09-06 起玩法收敛为唯一「复合玩法」（大吃小×撑庄合一，rule_fuhe.py）**：总后台 `play_rule_files` 只保留这一行（V1.0.11 迁移清理全部旧种子；管理页若手动删除该行，重启后 `ensureSeedRules` 会把内置种子兜底复活——**停用请用总后台启停状态，不要删行**）。agent 端启动/重启用时自动拉取激活该唯一玩法，「游戏玩法」页即手动操作台，不再有多玩法列表与启停切换。玩法设计史（v1/v2、红包计分、自动结算、多玩法）见 [玩法系统设计.md](玩法系统设计.md) 与 [玩法v2结算与上报设计.md](玩法v2结算与上报设计.md)，均仅留档；总后台对局上报/入账契约见仓库根 README「游戏对局结算」。

复合玩法的一局 = **群内文字下注/撑庄 + 管理员红包开奖 + 面板手动结算**：管理员在玩法面板点「开始本局」→ 群成员发数字下注、发「撑」即可撑庄 → 点「停止下注」封盘（@全体 播报下注汇总与需开奖人数）→ 管理员在群里发红包（每份 0.01~0.99 元，份数不少于需开奖人数）定每人大小 → 点「结算」开奖并上报总后台（每人收到个人开奖 @ 回复 + @全体 播报结算汇总）。**积分只经红包结算产生**：下注/撑庄全程 delta=0，不动任何积分；作废（无人下注/红包份数不足/庄家余额不足/手动「作废本局」）= 积分未扣、不上报。**群主/管理员（NapCat 登录 QQ）也是玩家**（只有机器人自己的发言不触发，防回环）。

### 8.1 消息流（三类回调事件 → 单队列 worker → 手动结算）

```

  纯文本非空 + qq≠self_id；message_sent 一律不转发，防 n+1 回环）

      ↓

  kind=message → _handle_one(870)：
     内置查分「查/查分/查积分」→ 局外基础玩法兜底（上100/下100 申请确认、局外下注提示、

### 8.2 玩法文件协议与引擎（integration/play_engine.py + play_rules/rule_fuhe.py）

玩法文件即 Python 源码（`rule_fuhe.py` 是当前唯一玩法：仓库 `agent/play_rules/rule_fuhe.py` 与总后台 `seed_rules/rule_fuhe.py` 同源）。引擎 `RuleEngine`（play_tab 持有单例）加载 `%APPDATA%\QQHongbaoMonitor\plays\rule_{id}.py`（`cfg.plays_dir()`，运行期下载落盘；开发态仓库 `agent/plays/` 下亦可有镜像）。入口 `engine.handle_message(group_id, qq, nickname, text) -> str|None`，回复侧自动 @；`engine.last_delta` 落最近积分变动、`engine.last_error` 落异常（**v3 复合玩法全程 delta=0**，积分只在 settle 阶段由 `settle_redpacket` 一次性计算）。

- **带返回值的可选协议**一律经 `engine.call_rule(fn_name, group_id, *args)` 调用、**返回值原样透传**（未激活/玩法无此函数/异常 → None 并记 `last_error`；GUI 操作台不猜类型，按协议结构自行解析）。复合玩法用到的函数：

| 函数 | 用途 / 返回 |
|---|---|
| `handle_round_start(group_id, round_id) -> str` | 「开始本局」：重置该群入 betting，返回开场白（@全体 播报局号） |
| `handle_seal(group_id, rate_permille=20) -> dict` | 「停止下注」封盘：`{ok, text, banker_check, img?}`（R7 起带 img 结构化表格 `{caption, headers, rows, right, footer}` → GUI 渲染成图片 @全体）；ok=False（无人下注/非下注期）或撑庄局 `banker_check.need`(=下注池+抽水) 超过庄家余额 → 作废关局，积分未扣。GUI 侧再分流：**无进行中的局**的停注提示只记玩法日志不发群；无人下注才 @全体 播报作废 |
| `seal_info(group_id) -> dict` | 局快照（无局/复位返回 `{phase:'idle',...}`，**不是 None**）：phase=idle/betting/sealed、mode、round_id、boss、n_bets、pool、fee、claim_need；按钮门控/状态栏数据源 |
| `bet_snapshot(group_id) -> list` | 注序下注明细（GUI 开奖表行数据源；有庄末尾追坐庄行 `{qq, nickname, amount:0, boss:True}`；无局空 list） |
| `claim_need(group_id) -> int` | 需开奖人数 = 下注人数 + 有庄 1 份（庄家也需 1 份定自己点数）；非下注/封盘期=0 |
| `handle_redpacket(group_id, qq, nickname, amount) -> tuple[str\|None, int]` | 红包领取事件：正常领取回执空串 `""` = 已受理、记账但不发消息（不 @ 领取人）；金额非 0.01~0.99 返回警告文本提示修正；未参与/不在期返回 None（不记账）；delta 恒 0 |
| `settle_redpacket(group_id, claims, rate_permille=20) -> dict` | 封盘结算（claims 来自红包领取 + 开奖表双击改值，未领者按 0 点计）：返回 `{events: [{qq, nickname, delta(扣抽水后净额)}…]（v3.1 起无个人 reply，不逐人 @开奖）, announce: 短句, img?}`；announce = 「本局结果，总分 N 分」短句，明细走 img 表格（R7 起：按点数降序、同点数按下注顺序；撑庄局 footer 单列「庄家 X（点N）：净得 ±Y」，不含抽水）；img 渲染失败自动降级纯文本；无局返回 None |
| `handle_void(group_id) -> str\|None` | 作废公告并复位该群（红包不足/余额不足/手动作废共用；无进行中局返回 None）；`handle_round_abort` 旧协议在 fuhe 中为同义别名 |

- 无返回值/被动协议（引擎侧入口调用）：`handle_round_end(group_id)`（结算成功/关局后清态）、`handle_round_abort(group_id)`（旧「结束本局」问询，fuhe 兼容别名）、`bettor_qqs(group_id)`（引擎 `rule_bettors` 用）、`betting_open(group_id)`（agent 下注预检问询，见 play_engine.py:354）
- **引擎共性**：同 qq 1 秒内重复发言忽略（`DEDUP_WINDOW_SEC=1.0`）；文件 mtime 变化自动热重载（总后台重传 → agent 下载覆盖 → 下次发言即新逻辑；加载失败沿用旧版记 `last_error`）；玩法代码抛异常只记 `last_error` 不崩引擎；**玩法文件应快速返回，勿阻塞 IO/长循环**（worker 串行）
- **自测**：`python -m integration.play_engine`（激活/回复协议/v1&v2 返回值/delta/去重/热重载/坏文件/缺入口/call_rule 透传/RoundSession 多局结算/deactivate）

### 8.3 GUI「游戏玩法」手动操作台（gui/app/play_tab.py + integration/redpacket_game.py）

`PlayTab(ctk.CTkScrollableFrame)`（约 1450 行）：构造即拉起本地回调服务 + worker（daemon），`shutdown()` 挂进 `_on_close`(2185)。布局：状态行 + 群多选（勾选即推送插件转发名单并**即时落盘** cfg.play_group_id）+ 当前群切换 + 「开始本局 / 停止下注 / 结算 / 作废本局 / 更新玩法文件 / 重试未上报」+ 费率‰与最小下注 + 开奖表（每行 = 下注人或庄家，双击「抢到金额」改值、点数即时重算；R7 起改/补值各记一条 delta0 对局回放「管理员改开奖金额：旧→新 元」/「管理员补值开奖：X 元」，随结算上报，回放中可见）+ 玩法日志。

- **启动自动激活**（`_auto_restore`(1209) + 勾选变化即时落盘）：`HbjfClient.list_rules()` 取唯一玩法（没有则取第一条）→ 下载到 `plays/rule_{id}.py` → 插件 `/play/config {enabled:true, groups, callback}` → engine.activate → 自动同步成员（可选 `play_auto_register_members`）→ cfg.play_enabled=true 落盘。`cfg.play_rule_id/play_rule_name` 供上报使用
- **红包玩法会话**：玩法含 `handle_redpacket` 时 `_rp_build`(850) 构造 `RedPacketGame`（redpacket_game.py，手动结算驱动改造版）：注入 `rule_handler`（逐领取人 handle_redpacket）/`rule_handler_batch`（settle_redpacket）/`send_reply`/`send_announce`（@全体）/`settle`（上报总后台）/`get_admin_qqs`/`get_bettors`（rule_bettors）/`claim_need`（经 call_rule）。redpacket_game 内**分阶段自动收尾/领完自动结算已废弃**（`poll_auto_end` 为空壳，保留兼容调用）
- **每群独立一局**：round_id = `{seq:07d}`（R7 起纯数字递增 0000001…，不带玩法名前缀；`cfg.game_round_seq` 自增，开始本局落盘；后端 round_id 仅作 ≤96 幂等键）；对局状态存 rpg `announced[gid]` + 玩法模块态
- **按钮流**（`_gate_buttons`(519) 按 seal_info 门控）：
  - 开始本局（537）：无进行中局 → 开局 + @全体 播报开场白（含局号）
  - 停止下注（560）：`call_rule("handle_seal", gid, rate)` → 撑庄局先查庄家余额（`banker_check.need`=池+抽水，30s 缓存查询）不足即作废 → `rp.seal_round(gid)`（A3：封盘时已知首红包份数 < claim_need 则内部作废播报）→ 未作废 @全体 播报：短句「停止下注，合计 N 分」+ **下注汇总表格图**（R7：img 结构化表格经 table_image.py 渲染成 PNG，本地临时文件路径走插件 `image_file` 发群；渲染失败或图片被插件拒 → 自动降级纯文本兜底）；**无进行中的局**点停注 = 只记玩法日志、不发群（R7-2）；「请管理员发红包开奖（每份…）」尾巴已移除，开红包引导只留在玩法日志提示管理员
  - 结算（610）：要求 phase=sealed + 已见首红包；红包未领完需**再点一次确认**（`_force_ok`，未领者按 0 点结算输光）；worker 线程 `settle_round_now` → @全体 播报「本局结果，总分 N 分」短句 + **结算表格图**（R7；降级纯文本兜底）→ 开奖表补「结果」列（保留到下次开局；v3.1 起无逐人开奖 @）
  - 作废本局（675）：`call_rule("handle_void")` 文案 → @全体 播报 → 关局，**不上报不结算**
  - 更新玩法文件（`_reload_rule`(1292)）：重下载总后台最新版 → 覆盖本地 + 引擎热重载生效
  - 重试未上报（`_maybe_retry_rp_pending`(315)）：queue 空闲每 30s 兜底 `retry_pending`（token 修复/网络恢复自动补结算上报）；round_id 幂等防重复入账
- **封禁/停用停摆**：总后台封禁执行器（40310）/停用或禁手动操作员（40311）→ `_mark_banned`：引擎停、插件转发关、cfg.play_enabled=false；GUI 红字提示 + 日志引导去总后台处理；解封后重启 GUI（或重新启用）自动恢复：重拉最新玩法文件 + 续传未结算局（`_auto_restore`）

### 8.4 触发范围决策

全体成员触发（含群主/管理员/机器人使用者），**唯独机器人自己（post_type=message_sent 或 qq==self_id）不触发** —— 双保险写在 play.ts:46-54。玩法文件可自行用 qq/nickname 判断要不要理某人（协议参数都传了）；「开始游戏/开局」等管理员动作只认群主/管理员（`_rp_admin_qqs`，600s 缓存）。复合玩法下注期积分从未扣除，作废即无操作；扣/加积分只在结算时按 v2 语义产出 delta，玩法自己负责算分逻辑。

## 9. 打包系统

两个入口，都在 `agent\` 目录双击：

| | `打包exe.bat` | `build.bat` |
|---|---|---|
| 用途 | **快速出 exe 测试** | 完整交付包 |
| 步骤 | 定位 Python → 备 plugin_bundle（有 plugin\dist 就同步，没有就复用旧的）→ pip install → PyInstaller spec | `[1/5]` 插件 npm 构建（dist 已存在则跳过，无需 Node）→ `[2/5]` 备 plugin_bundle → `[3/5]` pip → `[4/5]` PyInstaller → `[5/5]` assemble_release.py 组装 |
| 产物 | `dist\agent.exe`（几十秒） | `release\`（解压即用）+ 根目录 `agent_交付包.zip`（几分钟） |
| 迭代建议 | 改 Python 代码后反复跑它 | 涉及插件/交付再跑 |

**PyInstaller spec 关键点（QQHongbaoMonitor.spec）**：

- `Analysis([gui/main.py], pathex=[GUI, ROOT], ...)` —— **仓库根必须进 pathex**，否则顶层 `integration/` 包进不了 exe（最易踩的坑）；
- datas：customtkinter 主题资源 + `(plugin_bundle, "plugin_bundle")` —— 插件 index.mjs 内嵌进 exe，部署插件时解出来（`sys._MEIPASS/plugin_bundle`）；
- excludes：numpy/cryptography/psutil 等重型无用依赖（缩体积）；
- `EXE(... console=False)`：onefile 无控制台。

**assemble_release.py（build.bat 第 5 步）**：清空重建 `release/` → `dist/*.exe` 拷成 `release/agent.exe` → 拷启动脚本 → `copytree tools/NapCat` 并 **strip 登录态**（删 cache/qrcode.png、guild1.db*、napcat_*.json、onebot11_*.json、passkey.json、logs —— 每台部署机独立扫码登录的设计就靠它）→ 预置插件 → 拷全部源码镜像进 `release/agent/`（gui/plugin/src/integration/client/scripts/plugin_bundle + 构建脚本 + README）→ 生成 `使用说明.txt`（utf-8-sig，Windows 记事本友好）→ 打 `agent_交付包.zip`（UTF-8 文件名）。

`write_release_doc.ps1`：独立生成使用说明的 PowerShell（文案更详），可单独跑刷新 release 里的文档。

| GUI 加按钮/加 tab | main_window.py 对应 `_build_*` 方法；**新线程必须在 _on_close 清理** | run_dev.bat |
| 总后台新增 open 接口 | integration/backend_client.py 加方法（照抄现有 `_get/_post` 模式） | 先 curl 总后台，再 smoke |
| agent 加远程命令 | 总后台下发新 command → `sync_worker.py _execute` 加分支 → 回报 | 下发后看 GUI 日志与回报结果 |
| 改动玩法逻辑 | 玩法文件是唯一 `rule_fuhe.py`（协议见 §8.2 表）：仓库 `agent/play_rules/rule_fuhe.py` 与总后台内置种子 `seed_rules/rule_fuhe.py` 同源，改总后台种子或上传新文件 → agent 玩法页「更新玩法文件」重下载热生效 | `python -m integration.play_engine`（把文件放 play_rules 会被 selftest 加载）+ 真群验证 |
| 新写一个玩法文件 | 复制 `play_rules/rule_fuhe.py` 起底（导 `handle_message` + 可选协议表 §8.2）；**别做阻塞 IO**（引擎单 worker 串行） | `python -m integration.play_engine`（自测加载仓库真实样本）+ 真群验证 |
| 改 GUI/插件后出包 | `打包exe.bat`（只改 Python）或 `build.bat`（全量） | dist\agent.exe 双击 |

**贯穿全文的三条红线**：① 线程纪律（worker 线程绝不碰控件，一律 after(0)）；② 命令/接口幂等（总后台会重投、会重复调用）；③ 登录态不入包不入 git（每台机器独立扫码）。
